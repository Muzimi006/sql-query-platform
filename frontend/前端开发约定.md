# 前端开发约定（设计系统 + 组件 + 接口语义）

> 这份文件是给**改前端的人（和 AI）**看的：动手之前先读它，避免出现"同一个按钮三种写法"。
> 前端**刻意零 UI 依赖**（没有 Element Plus、没有图标库）：少一层依赖就少一次装不上/离线构建失败的机会。

## 一、技术栈与目录

```text
frontend/
  index.html            vite 入口
  vite.config.js        开发期把 /api 代理到 8080（所以浏览器眼里前后端同源，不需要 CORS）
  src/main.js           createApp + router + 全局样式
  src/App.vue           外壳：侧边栏 / 顶栏 / 主题切换 / 全局 toast / 全局确认框
  src/router.js         路由（懒加载 + 登录守卫；meta.title 就是顶栏标题）
  src/api.js            所有接口调用（按业务分模块）
  src/auth.js           登录态（⚠️ token 放在 ref 里，理由见文件顶部注释）
  src/ui.js             toast / confirmDialog / copyText
  src/format.js         时间、数字、状态字典、SQL 摘要
  src/style.css         设计系统（变量 + 全部组件类）
  src/components/       AppIcon / AppEmpty / AppPager / AppDrawer / StatusTag
  src/views/            页面
```

## 二、后端语义（写前端必须遵守）

| 事实 | 含义 |
|---|---|
| **HTTP 永远是 200**，业务结果在 body 的 `code`（200 成功 / 500 失败）| 不能只看 HTTP 状态码判断成败；axios 拦截器已经把失败包成 rejected Promise 并带上 `message`，调用点 `try/catch` + `toastError(e)` 即可 |
| 401 由 `JwtInterceptor` 直接写出 | 拦截器统一清 token 并跳登录，页面不用管 |
| 分页返回 `{ records, total, size, current, pages }` | MyBatis-Plus 的 IPage 结构 |
| **批准 / 提交导出都是异步的** | 接口返回 200 ≠ 执行完成，必须轮询详情或列表 |
| 限流命中返回业务失败（"提交太频繁，请稍后再试"） | 正常提示即可，**不要自动重试** |
| 出参永不下发数据源密码 | 编辑数据源时密码留空 = 不修改 |

## 三、设计系统（只准用这些类名）

颜色、圆角、阴影全部走 CSS 变量（`src/style.css` 顶部）。**不要写死 `#xxx`** —— 写死的地方深色模式一定会漏。

### 6.1 幂等键（`requestToken`）怎么用

提交工单 / 生成 SQL 时带 `requestToken`：**同一次提交意图用同一个 token**。
正确做法是弹窗打开时 `newRequestToken()` 生成一个，提交成功后清掉；
提交失败重试时**沿用同一个** —— 这才是幂等。
⚠️ 换了 SQL 却复用 token，后端会按"载荷不一致"直接报错，这是有意的设计。

### 6.2 ⚠️ 已知脆弱点：NL2SQL 页的失败分支是靠**文案子串**匹配的

`Nl2SqlView.vue` 要按失败原因给不同建议（安全校验未通过 / 类型不受理 / 这是一句查询需求 / 信息不足 / 频率限流 / 并发限流 / 未启用），
但后端的失败原因**全在 `message` 里**（HTTP 恒 200，没有错误码字段），所以前端只能匹配文案：

| 前端匹配的串 | 来源 |
|---|---|
| `这是一句查询需求` | `NaturalLanguageSqlService`（模型给了 SELECT 时）|
| `不在工单受理范围内` | 同上（DDL 等）|
| `没有通过安全校验` | 同上（四道防线拦下模型输出）|
| `生成太频繁` / `当前生成任务较多` | 控制器里的频率与并发限流 |
| `未启用` | `DisabledLlmClient` |

**后果**：后端改一句文案，对应分支就**退化成通用失败提示**（不崩、不报错，只是少一条可操作的建议）。
⭐ 更稳的做法是后端在失败时带一个**错误码**字段（例如 `code: 500` + `reason: NL2SQL_SELECT_NOT_REVIEWABLE`），
前端按码分支、按 message 展示 —— 这一条**记在案但没做**（改响应契约要同步 OpenAPI 契约测试与前端，属于另一轮）。

同一处还有个同类写法：那句「这是一句查询需求」的提示**把模型生成的 SELECT 拼在消息末尾**，
前端只能从末尾切出来再显示在查询页入口上。同样应该结构化。

### 6.3 已知缺口：这两件事**要后端配合**才能做得更好（登记在案，本轮不做）

| 缺口 | 现状 | 要改就得动后端 |
|---|---|---|
| **行内「测试连接」点不了** | `/datasource/test` 收的是完整 `DbSourceDTO`（含密码），而出参**永不下发密码** —— 所以列表行上的「测试」只能"打开弹窗 + 提示补密码"，真正的测试按钮在弹窗里 | 需要一个只按 id 测的接口（`POST /datasource/{id}/test`，服务端解密后自己连）。⚠️ 新增接口会动到接口计数文档与 `OpenApiContractIntegrationTest` 的接口总数断言，属于另一轮 |
| **导出列表不分页** | `/export` 返回全部任务（后端没有分页版），所以导出页没接 `AppPager` | 后端加 `GET /export/page`。任务量大时才需要，目前量级可以接受 |
| **工单里看不到数据源名** | `SqlReviewRequestVO` 没有 `dataSourceName`，而 `GET /datasource` 只返回**自己的**数据源 —— 所以「待我审批」队列里别人名下的数据源只能显示 `#id`（title 里已标注）| 后端 VO 补 `dataSourceName`（顺带 `submitterName` 更好）|
| **四眼原则只能靠报错发现** | VO 里没有 `submitterId`，前端**无法预判**"这条是我自己提的、批准会被拒"，只能等业务失败 toast。另外 `pending` 队列不区分提交人，管理员自己的待审工单也在队列里 | 后端 VO 补 `submitterId`（前端就能把"批准"按钮禁掉并说明原因）|

> 💡 改前端之前先跑一次 `node scripts/check-sfc.cjs`：它不构建、不起服务，
> 只解析 `.vue`，能抓到语法错误、模板里拼错的变量名、忘了 import 的组件 ——
> 而 `npm run build` 要跑完整条依赖图，多个人同时改时谁都验不了自己那个文件。

### 6.4 跨页面带参：历史 / 收藏 → 查询页

```js
router.push({ path: '/query', query: { sql: item.sqlText, dataSourceId: item.dataSourceId } })
```

查询页挂载时读 `route.query.sql` 回填表单，然后 `router.replace` 把参数清掉（避免刷新重复带入）。

## 七、写页面的硬要求

1. 必须有**加载中态 / 空态（AppEmpty）/ 错误 toast / 提交中禁用按钮**四件套。
2. 异步任务的页面必须**轮询**并**在卸载时 clearInterval**（导出列表、工单详情）。
3. 破坏性操作（删除、清空、停用、驳回）一律 `confirmDialog`。
4. 时间用 `fmtRelative` + `title` 放绝对时间；数字用 `fmtNumber`；状态一律 `StatusTag`。
5. 注释写**为什么**和**坑**，不写"这行在赋值"。
6. **不要引入任何新依赖**；**不要跑 `npm run build`**（多人并行改时构建会互相干扰，由集成方统一构建）。
