# 开发规范（本项目实际遵循的，以及有意不遵循的）

> ⚠️ 这份文件的写法是「**先说结论、再说为什么、最后给证据**」，和项目其它文档一致。
> 里面每一条要么能指向一个真实文件/配置，要么明确标成**约定**（靠人遵守，工具管不了）。
>
> **它和 `docs/ai-assisted-development.md` 的分工**：那份讲「和 AI 怎么协作」，
> 这份讲「代码、提交、配置、依赖长什么样才算合格」。

---

## 一、提交规范：Conventional Commits

格式（[conventionalcommits.org](https://www.conventionalcommits.org/zh-hans/v1.0.0/)）：

```text
<type>(<scope>): <描述>

<正文：为什么这么改、权衡是什么>

<脚注：Closes #12 / BREAKING CHANGE: ...>
```

| type | 什么时候用 |
|---|---|
| `feat` | 新增对外可见的能力（接口、配置项）|
| `fix` | 修 bug |
| `chore` | 构建、依赖、脚本、部署文件 |
| `docs` | 只改文档 |
| `test` | 只改测试 |
| `refactor` | 对外行为不变的内部调整 |
| `perf` | 性能相关 |

**⚠️ 本项目在描述和正文里用中文**，type 用英文 —— 约定优先保证「机器可解析」，其次是「人读得懂」。

**正文的要求比 type 更重要**：本项目的提交正文一律写清
「**原来的行为是什么、会造成什么后果、为什么这样改**」，
因为半年后回看 `git log` 的人（包括作者自己）需要的正是这三句话。

> 检查方式：`git log --oneline -20` 应当能一眼看出每条的类型；
> 看不出来就是没按规范写。

## 二、代码规范

### 2.1 语言与格式

| 项 | 约定 | 由谁保证 |
|---|---|---|
| 缩进 / 行尾 / 编码 | 4 空格（yml、json、前端 2 空格）、LF、UTF-8 | `.editorconfig` + `.gitattributes` |
| Java 版本 | 17（`maven.compiler.release`）| `maven-enforcer` 的 `requireJavaVersion [17,)` |
| 命名 | 包名小写、类名 UpperCamel、方法与变量 lowerCamel、常量 UPPER_SNAKE | 约定 |
| 注入方式 | **一律构造器注入**，不用字段注入 | 约定（代码里没有一处 `@Autowired` 字段）|
| Lombok | 只用 `@Slf4j` / `@Data` 这类，**不生成构造器替代构造器注入** | 约定 |

### 2.2 注释：本项目最硬的一条要求

**注释写「为什么」，不写「做什么」。** 具体到可检查的程度：

1. **每一个不明显的决定都要写理由**，包括「为什么不用那个更常见的做法」；
2. **保护性代码要写清它防的是什么**，否则后人会把 `if` 当成多余的分支删掉；
3. **踩过的坑要在注释里留证据**（实测数字、报错原文、反向验证的输出）；
4. **不确定的事必须标出来**：是「实测」还是「推断」，一句话之差。

> 证据：`SqlPlatformMetrics` 里解释了「为什么 Counter 不带 dataSourceId 标签」（指标基数泄漏）、
> `ExportConsumer` 里留了 ack 异常被误判的完整推理、`DbSourceCircuitBreaker` 里写了 cause 丢掉会怎样。

### 2.3 分层与职责

```text
controller  —— 参数校验（@Valid）、限流、取当前用户；不写业务规则
service     —— 业务规则、事务、并发闸门、熔断
mapper      —— 只做数据访问；条件更新（WHERE status = ?）表达幂等
aspect      —— 横切关注点（审计）；**不允许在这里做业务判断**
```

**「保护措施放在资源之前」** 是本项目的一条硬约定：
并发闸门、限流、熔断都必须发生在**碰到数据库/外部服务之前**，
否则保护措施自己会变成成本的来源（见 G-07）。

### 2.4 异常

- 业务失败 → `BusinessException`（**必须带 message**，因为它是给用户看的那句话）；
- **包装底层异常时必须把 cause 带上** —— 否则所有「按异常类型判断」的逻辑（熔断、重试）全部失效，
  而这是一个静默失效（本项目真的发生过：熔断器因此永远不会打开）；
- 「在碰到任何资源之前就被拒」→ `RejectedBeforeWorkException`（继承 BusinessException），
  让上层能区分「没做事」与「做了但失败」；
- 兜底分支必须留计数器（`system.error`）—— 因为本项目错误响应是 HTTP 200 + code，
  任何按 HTTP 状态算错误率的监控都是瞎的。

## 三、测试规范

| 项 | 约定 |
|---|---|
| 需要中间件的用例 | 打 `@Tag("integration")`，默认不跑（`surefire.excludedGroups`）|
| 纯单元用例 | 不得依赖 Spring 上下文；需要 `TableInfo` 缓存时手工 `TableInfoHelper.initTableInfo(...)` |
| 命名 | 测试类 `XxxTest`；方法名描述**失败模式**而不是方法名 |
| 显示名 | `@DisplayName` 用中文写「这条用例守的是什么」 |
| **反向验证** | 修 bug 时**必须做**：把 bug 造回去，确认新用例变红（见下）|

### ⭐ 3.1 反向验证是本项目的硬性要求

```text
用例全绿有两种可能：修好了，或者这条用例根本测不到那件事。
只有「把 bug 造回去会变红」才能把两者分开。
```

做法：临时改回旧实现 → 跑那一条用例 → 确认失败信息正是你预期的失败 → 改回来 → 全绿。
档案里每一轮修复都附了这段输出（例如 `expected: <5.0> but was: <0.0>`）。

## 四、依赖与构建规范

1. **覆盖 Spring Boot 管理的版本，必须写进 `<dependencyManagement>`**，不能写在直接依赖的 `<version>` 上 ——
   后者会让依赖树里同时存在两个版本（`dependencyConvergence` 会失败，运行时表现为诡异的 `NoSuchMethodError`）；
2. **覆盖受管版本必须写明原因**（CVE / 功能修复 / 只是跟着升级）；
   写不出原因的就应该删掉覆盖、交回 Boot 管理；
3. 构建环境要求由 `maven-enforcer` 强制（JDK ≥ 17、Maven ≥ 3.9、依赖收敛），
   CI 跑 `mvn -B verify` 而不是 `test`，这样这些检查一定被执行；
4. 新增依赖前先问一句：**Boot 的 starter 里是不是已经有等价能力**。

## 五、配置规范

每一个新配置项必须同时给出三样东西，缺一不可：

1. **默认值**（写在 `@Value("...:默认值")` 和 `application.yml` 两处，保持一致）；
2. **一句话说明它影响什么**；
3. **⚠️ 不配 / 配错会怎样** —— 这一条是本项目反复吃亏的地方
   （例如 `retention.*-days` 配成 0 会删光整张表，所以代码里做了「≤ 0 就跳过并告警」）。

其它约定：

- **凭据一律只从环境变量注入**（`DB_PASSWORD` / `JWT_SECRET` / `AES_KEY` / `LLM_API_KEY` / `ADMIN_REGISTER_CODE`），
  不写进配置文件、不提交进仓库；
- 保护性配置**配错时选「损失更小」的方向**，并且不得让应用起不来：
  限流器在 Redis 不可用时放行、时区串非法时沿用默认值、并发上限配 0 时按 1 处理；
- 每一个「默认关闭」的功能都要在配置旁边写清**为什么默认关闭**（如 `retention.enabled`、`platform.llm.enabled`）。

## 六、⚠️ 规范偏差登记（有意不遵循，以及理由）

> 这一节比前面五节更重要：**不规范不可怕，说不清为什么不规范才可怕。**
> 每一条都可以被重新讨论，但讨论之前需要知道现状。

| # | 主流规范 | 本项目的做法 | 为什么 | 什么时候可以改 |
|---|---|---|---|---|
| 1 | 错误响应用 **HTTP 4xx/5xx**（RFC 9457 Problem Details）| **HTTP 200 + body 里的 `code`** | 前端与文档全部按 `code` 判断；改状态码等于改接口契约。代价是**任何按 HTTP 状态算错误率的监控都是瞎的**，已用 `system.error` 计数器补偿 | 需要前端同步改动 + 网关告警规则重写时。属于一次性的大改，不做半套 |
| 2 | REST 路径带版本号（`/api/v1/...`）| `/api/...` | 目前只有一个消费方（自带前端），没有并行版本的需求 | 出现**外部**消费方时 |
| 3 | 仓库带 `LICENSE` | **没有** | 这是**作者的意愿问题，不是技术问题** —— AI 不应该替作者选许可证 | 作者决定后一行文件即可 |
| 4 | 保留策略默认开启 | `retention.enabled: false` | 删除不可逆，而「保留多久」是业务/合规决定 | 部署方在明确合规要求后开启 |
| 5 | 监控端点对外可抓取 | 默认 `127.0.0.1:8081` | `/actuator` 里有能读到内部信息的端点；要跨机抓取应走带鉴权的网关 | 已经有网关时（现在地址已可配）|
| 6 | 全项目统一格式化（如 google-java-format）| 只有 `.editorconfig`，**没有强制格式化插件** | 引入后会重排整个代码库（大量与本次改动无关的 diff），而本项目注释密度很高，格式化对注释几乎无收益 | 想引入时先单独做一次「只格式化、不改逻辑」的提交 |
| 7 | 覆盖率门禁（JaCoCo 阈值）| 无 | 覆盖率不等于有效性（本项目更依赖反向验证）；先有覆盖率曲线再谈门禁 | 接完 CI 覆盖率报告之后 |
| 8 | 迁移脚本由工具自动执行（Flyway/Liquibase）| `sql/migrate_00X_*.sql` **手工执行** | 已在 README 与交接文档写明「迁移脚本不会被应用自动执行」，且踩过一次漏执行的坑（被集成测试抓出来）| 引入 Flyway 需要先给现有 8 张表做 baseline，单独一轮 |

- 新增规范条目时，**必须同时写「谁保证」**（工具 / 约定）——
  靠人遵守的条目要尽量少，并且明确标出来；

- 规范变化属于**对外可见的变化**，要同时更新 `CHANGELOG.md`。
