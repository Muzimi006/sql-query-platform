# AI 辅助开发实践

这个仓库，以及我在 openGauss 社区的开源实习，是我把 AI 当**工程工具**而不是**补全器**用的实践记录。

下面写清楚四件事：**我用什么工具、怎么把任务交给 AI、卡在哪里、怎么判断它给的结果能不能用。**

---

## 一、工具与分工

| 工具 | 我用它做什么 | 为什么是它 |
|---|---|---|
| **Claude Code** | 陌生代码库里的定位与改造（openGauss 内核 C/SQL）、跨多文件的批量修改、写回归用例、环境问题排查 | 能自主读文件、跑命令、看输出再改，适合"改完要验证"的活；项目里用 \`.claude/settings.json\` 固定了允许执行的命令白名单 |
| **DeepSeek API** | 长文本处理：PR 评论与 CI 日志分析、文档批量生成与校对、回复草稿 | 长上下文便宜，适合"喂一大段日志，要一个结论" |
| **DeepSeek Harness** | 工作流编排（Skill / Subagent / Workflow）、目标驱动开发、上下文工程 | 把重复性任务沉淀成可复用的流程，而不是每次重新聊一遍 |
| **自写脚本（AI 辅助生成）** | PowerShell / Bash 批量拉取 PR 与 CI 数据、**8 个 JDBC 驱动版本 × 3 个框架的矩阵扫测**、日志解析与报告产出 | 批量、确定性、可重复的事，交给脚本比交给对话可靠 |

分工原则很简单：**要"想"的给模型，要"跑"的给脚本，要"信"的给测试。**

---

## 二、我的方法：目标驱动 + 可验收

### 1. 先定验收标准，再让 AI 动手

我不会说"帮我实现 mod 函数支持 blob"。我会先把**怎么算做完**写下来：

> ① blob 调 \`mod()\` 不再报 \`function is not unique\`
> ② 跨类型组合全部有精确签名
> ③ 每条期望值先在 MySQL 上真实执行过
> ④ \`make check\` 全绿且不破坏既有用例

有了这四条，AI 的产出**可以被判定**，而不是"看起来像对的"。

**如果一件事我说不清怎么验收，说明我还没想清楚要做什么** —— 这时候不该动手。

### 2. 上下文要固化成文件，而不是留在对话里

对话会丢，文件不会。所以我把"它必须知道的东西"写进仓库：

- 项目规范、目录约定、命名习惯、禁止事项 → 写成配置文件放在仓库里
- 环境信息（IP、端口、库名、启动命令）→ 写成文档
- 一次任务的结论（哪个方案被否掉了、为什么）→ 写进任务记录

这样下次开工不用从零复述，新会话也能立刻进入状态。

### 3. 小步提交，每步都能验证

改一点 → 跑一次 → 确认 → 再改。不攒一个大改动最后一起验证 —— 出问题时你分不清是哪一步引入的。

### 4. 机器验证优先于人眼 review

这条是花钱买来的教训，见下面「踩过的坑」第 4 条。

## 三、案例 A：openGauss dolphin 插件 mod / round 支持二进制类型

**S｜背景**
openGauss 的 B 兼容库中，\`mod()\` / \`round()\` 传入 blob / binary 等二进制类型时报
\`function mod(blob, integer) is not unique\`：函数解析器找不到精确匹配时走隐式转换搜索，
而 blob 存在多条代价相同的转换路径，无法唯一决定。

**T｜任务**
让这两个函数完整支持二进制入参并覆盖跨类型重载，**行为与 MySQL 逐项对齐**，且不破坏插件安装与既有回归。

**A｜做法**
- 先用 AI 在 12000+ 文件的仓库里定位到 dolphin 插件的升级脚本与 C 函数实现，摸清函数解析与重载注册的机制
- 定实现路线时**否掉了"每个签名写一个 C 函数"**：约 110 个重载签名各写一个 C 函数，改动面和风险都不可控
- 最终方案是**最小改动**——C 层各加 1 个函数（\`b_numeric_mod\` / \`b_double_round\`，边界语义如除零返回 NULL、NaN 都在里面处理），
  SQL 层用 \`LANGUAGE SQL\` 包装函数把入参 cast 后委托给它。**内核解析逻辑一行不动。**
- 约 110 个重载签名由 AI 按模板批量生成，**我逐条复核**：返回类型归属、\`IMMUTABLE\` / \`STRICT\` 声明、
  以及 \`CREATE OR REPLACE\` 不能改返回类型这个坑

**R｜结果**
新增 **39 条**回归用例，\`make check\` 全部通过；每条期望值都先在 MySQL 上真实执行对过账。
相关 PR：opengauss/Plugin #2523 / #2529。

**卡点 1：\`CREATE OR REPLACE\` 不能改返回类型**
master 上已有 \`round(binary, uint4)\` 返回 \`number\`，新语义要统一成 \`float8\`，
而 \`CREATE OR REPLACE\` 只允许改函数体。必须 \`DROP FUNCTION IF EXISTS\` 再 \`CREATE\`。
**这个坑的表现极具误导性**：错误发生在 \`create extension dolphin\` 装插件的时候，
整体失败 → 所有测试 \`exit 2\` → 输出全空，看不出任何函数级的错误信息。

**卡点 2：AI 给的测试用例数值被类型静默截断**
\`cast('1234567' as varbinary)\` 不写长度时默认长度只有 1，字符串被截成 \`'1'\` ——
测的已经不是目标行为，而是类型转换行为。\`cast('1.5' as uint8)\` 同理，会先按整数截断。
**AI 不知道你的类型语义，它会给你一个"语法正确"的用例。**

**怎么判断结果可靠**
1. 跑回归测试，期望值和实际输出逐行 diff
2. 期望值**不来自 AI**，全部先在 MySQL 上真实执行取得
3. 全仓 grep 确认没有其他测试文件用 blob/binary 调这两个函数，保证局部全绿等价于全量
4. CI 兜底

## 四、案例 B：8 个 JDBC 驱动版本 × 3 个框架的兼容性矩阵扫测

**S｜背景**
openGauss B 协议（MySQL 协议兼容口）需要给出「客户端用哪个驱动能连」的准确结论。
官方文档只写了一句"MySQL JDBC 8.0.28 及其以下"，但**新版本不一定不支持**，边界需要实测。

**T｜任务**
把"哪些驱动版本可用"从一句话变成一个**可复现的结论**。

**A｜做法**
- 把任务拆成**六维度矩阵**：框架（Spring Boot / Spring Data JPA / Spring Batch）× 驱动版本（8.0.28 ~ 26.7.0 共 8 个）
  × 新旧两套 Maven 坐标 × 连接与 CRUD 用例集
- 用脚本生成并批量执行：每个格子独立建工程、跑用例、落日志
- AI 负责的是**日志解析与差异归纳**，不是判定"能不能用" —— 判定标准是脚本的断言结果

**R｜结果**
产出测试思维导图与自测报告（opengauss/examples #110 / #111）。
过程中还**发现并定性了多个服务端兼容性差异**：

- \`LIKE ... ESCAPE\` 对反斜杠的转义行为与 MySQL 不一致
- \`information_schema\` 表名大小写敏感，与 MySQL 的 \`lower_case_table_names\` 语义不同
- \`SERIALIZABLE\` 隔离级别被**静默降级**，不报错但实际行为不符

这些不是"跑失败了"，而是**跑通了但结果和预期不一样** —— 这类问题最容易漏，因为自动化测试只会告诉你 exit code。

**怎么判断结果可靠**
每个格子都有独立的日志文件与运行记录，结论可以追溯到原始输出，而不是"我印象里好像不行"。

## 五、案例 C：这个仓库（SQL 查询与审核平台）

这个项目的后端同样采用**AI 辅助 + 人工验收**的方式完成，配置类和样板代码（DTO / VO / Mapper / 前端接口）由 AI 出稿，
**关键路径上的判断由我定**，并且在实现后专门做过一轮 review 清理。

被清掉的 AI 残留：

- \`QueryServiceImpl\` 构造器注入了 \`AesUtil\` 但**从未使用**（上下文漂移的典型产物）
- \`doExecute\` 里成片的空行、缩进错位，以及 \`// result set moved to inner try below\` 这种**过程性注释**
  —— AI 把"我改了什么"写进了代码里，但那是 commit message 该干的事
- 魔法数字直接内联（超时秒数 \`30\`），没有提取常量

我从两个角度审视它：**AI 生成后有没有人 review**，以及**关键逻辑有没有测试兜底**。
没有测试覆盖的地方，就是我必须逐行看的地方。

## 六、踩过的坑：AI 在这些地方会失效

### 1. 它会给你「语法正确但语义错误」的东西
见案例 A 卡点 2。类型截断、隐式转换、溢出边界 —— AI 不知道你这类领域语义。

### 2. 它不知道你环境里的隐性约束
\`CREATE OR REPLACE\` 不能改返回类型、插件安装失败会导致所有测试输出为空 ——
这些不是"通用编程知识"，是**这个项目的约束**。要靠上下文喂给它，否则它一定会踩。

### 3. 它的改动是自洽的，但不是最小化的
它倾向于"为每个情况写一份实现"。案例 A 里如果不主动否掉，就会变成 110 个 C 函数。
**"最小改动"这个约束必须由人来提。**

### 4. 最危险的不是它写错，是你没验证就提交
这个仓库有一次提交里带了**编译错误** —— \`DbSourceServiceImpl\` 里
\`objectMapper.writeValueAsString()\` 抛的是受检异常 \`JsonProcessingException\`，
外层 \`try\` 只有 \`finally\` 没有 \`catch\`。

那段代码是连带改的，IDEA 的增量编译没报出来，我又没跑完整的 \`mvn clean compile\` 就提交了。
**是后来加 CI 的时候被 CI 抓出来的。**

这件事之后我的习惯变成了：**每次改完必须跑一遍完整的编译 + 测试，再交给 CI 兜底。**
肉眼看代码的通过率，远低于跑一次构建。

## 七、我的验收清单

交给 AI 干活之前和之后，我会过一遍这几条：

**动手之前**
- [ ] 我能说清"怎么算做完了"吗？说不清就先别动手
- [ ] 这个任务有没有**机器可判定的**验收标准（测试 / 断言 / diff）？
- [ ] 有没有"最小改动"的约束需要我明确提出来？

**拿到结果之后**
- [ ] 期望值是从哪来的？**是 AI 编的，还是从真实环境取的？**
- [ ] 我跑过完整的构建和测试了吗？（不是只看 IDEA 有没有红线）
- [ ] 边界情况是谁负责想到的？入参为 NULL / 零 / 超长 / 类型不符会怎样？
- [ ] 这个改动有没有打破别的地方？有没有全仓搜索过调用点？
- [ ] 这段代码如果三个月后别人来读，注释和命名说得清意图吗？

**没跑通的、没验证过的，我不会说"完成了"。**

## 八、还没做好的

- **上下文固化还不够系统**：目前是散落的配置文件和文档，没有形成稳定的项目级规范模板
- **人工复核依赖状态**：110 个签名那条路走下来，复核质量和我当天的状态强相关，需要更机械化的检查（比如脚本化的签名比对）
- **测试覆盖仍然偏工具层**：服务层的关键路径（导出链路、连接池失效、缓存击穿）主要还是靠集成测试与人工验证
