# SQL 查询与审核平台

[![CI](https://github.com/Muzimi006/sql-query-platform/actions/workflows/ci.yml/badge.svg)](https://github.com/Muzimi006/sql-query-platform/actions/workflows/ci.yml)

一个基于 Spring Boot 的在线 SQL 查询与审核平台，提供用户认证、多数据源管理、SQL 安全校验、查询历史与收藏、异步导出、接口限流与操作审计能力。

仓库地址：https://github.com/Muzimi006/sql-query-platform

## 核心设计

本章说明各模块的关键设计决策与取舍，功能清单见后文。

### 1. SQL 执行的四道防线

平台需要连接用户自行配置的业务数据库，而用户提交的 SQL 属于不可信输入，因此在执行前设置分层拦截：

| 层 | 手段 | 拦截对象 |
|---|---|---|
| 解析层 | JSqlParser `parseStatements` + 语句类型白名单（**默认拒绝**） | 多语句注入（`select 1; drop table x`）、非 SELECT 语句 |
| 语义层 | **基于 AST** 检查危险函数与系统库（按方言取名单） | `sleep` / `load_file` / `pg_sleep` / `pg_read_file` 等；`mysql` / `information_schema` / `pg_catalog` 等 |
| 字符串兜底层 | 可执行注释、`INTO OUTFILE`（先屏蔽字符串字面量） | 解析器看不见的东西 —— 见下 |
| 资源层 | `setMaxRows(1000 + 1)` + `setQueryTimeout(30s)` | 大结果集占用过多内存、慢查询长期占用连接 |
| 数据库层 | 建议配合只读账号 | 应用层被绕过后的兜底 |

> 查询链路与导出链路共用同一个校验入口（`SqlValidateUtil`）。
> 导出**刻意比查询更严**：固定只允许 `SELECT`，不跟随角色白名单 ——
> 导出的语义是"把查询结果写成文件"，一条 `UPDATE` 也"执行成功"却没有可写进 CSV 的结果集。

#### 为什么是 AST + 两个字符串兜底，而不是纯 AST

早期版本的关键字层是对原始 SQL 做 `contains`。它两个方向都有问题，且都在真实 MySQL 上复现过：

| SQL | 旧实现 | 原因 |
|---|---|---|
| `select sleep/**&#47;(1)` | 🔴 放行 | 实测执行了 1057ms —— 注释把 `sleep(` 拆开了 |
| `select SLeeP (1)` | 🔴 放行 | 函数名与括号之间有空格 |
| `select count(*) from \`mysql\`.\`user\`` | 🔴 放行 | 检查的是 `"mysql."`，反引号把点隔开了 |
| `select 'sleep(1)' as note` | 🔴 **误杀** | 字符串字面量里出现这几个字符就被拒 |

改成 AST 后判断依据变成"这里是不是一次函数调用 / 一张表"，上述四条全部正确处理。

**但纯 AST 不够**：MySQL 的**可执行注释** `/*! ... */` 里的内容会被数据库真正执行
（实测 `select /*!50000 sleep(1)*/ as x` 耗时 1096ms），而 JSqlParser 把它当普通注释**整个丢掉** ——
AST 里只剩一个干净的 `SELECT 1`。所以这一类只能回到原始字符串判断，
并配一个"先屏蔽字符串字面量"的扫描器避免误杀。

**边界要说清楚**：这套检查挡的是"手滑和顺手"，不是"铁了心的攻击者"。真正的兜底是数据库侧的只读账号。

### 2. 动态多数据源连接池

数据源由用户在运行期自行添加、数量不固定，因此无法采用 Spring 的静态多数据源配置，改为按数据源记录动态创建与销毁连接池：

- 每个数据源对应一个独立的 HikariCP 连接池，缓存在 `ConcurrentHashMap` 中
- 数据源**修改 / 删除 / 禁用**时同步 `evict` 并关闭旧连接池。若不做 evict，连接信息变更后仍会继续复用旧连接池，且已被移除的数据源所对应的连接池无法释放
- 连接信息从 Redis 缓存读取，缓存未命中时回源数据库
- 驱动类名由方言显式指定，**不靠 Hikari 从 URL 推断** —— 支持多种数据库后 classpath 上会同时存在多个驱动，推断一旦猜错，报错是"driver not found"这类看不出根因的信息
- 连接池水位通过 Micrometer 暴露（`datasource.pool.connections.*`），并在驱逐时显式注销指标

#### 多实例部署：为什么需要广播，以及广播的到底是什么

一个容易搞错的点：**数据源缓存不在进程里，它就在 Redis 里**。
所以 `delete` 键这一步本来就是全局生效的，其它实例下次读就是 miss。

真正只存在于单个 JVM、别的实例看不见的是**连接池**。
实例 A 改了数据源密码之后，实例 B 手里那把池子**还在按旧密码连**，
表现为请求随机落到"能用"和"不能用"两种实例上 —— 是最难排查的那类故障。

因此数据源变更时会通过 Redis 发布订阅广播（`datasource:cache:invalidate`），
每个实例收到后清掉**自己的**连接池。

### 3. 缓存一致性与失效场景

数据源元数据缓存 30 分钟，并针对三种典型失效场景分别处理：

- **穿透**：查询不存在的记录时缓存空值（`"NULL"`，5 分钟 TTL），避免请求持续落到数据库
- **击穿**：两层锁。**JVM 内分段锁**（64 段）保证同一 key 在本进程内只有一个回源者；
  跨实例再由 **Redis 分布式锁**（唯一 token + Lua 脚本释放）兜底，
  没抢到锁的走**有界轮询等待**（每 20ms 读一次缓存，最多 500ms），等不到才自己回源并打 WARN
- **雪崩**：TTL 附加随机值（+0~300 秒），避免大量 key 同时过期

> **击穿那一层是"根除"而不是"降低概率"。**
> 早期实现是"抢不到锁就 `sleep(50)` 再读一次缓存，还没命中就直接查库" ——
> 等待者最终仍然会查库，QPS 一高照样打穿，而且 50 毫秒是拍脑袋定的。
> 现在用 32 个线程 + `CountDownLatch` 卡在同一时刻放出去，断言**数据库只被回源 1 次**。

数据源变更时，**缓存与连接池同时失效**。

### 4. 限流的原子性

两种算法均在 **Redis 内通过 Lua 脚本原子执行**：

- **固定窗口**：`INCR` 与首次 `PEXPIRE` 必须原子。分两步下发命令时，若进程在中间退出，该 key 将永不过期，对应用户会被**永久限流**
- **滑动窗口**：以 ZSet 记录每次请求的时间戳，任意长度窗口内计数精确；member 使用「时间戳 + UUID」保证唯一。若以纯时间戳作为 member，**同一毫秒内的并发请求会互相覆盖**，导致计数偏少、限流被绕过

### 5. 密码与凭据

- **用户密码**：BCrypt 哈希。仅引入 `spring-security-crypto`，不引入完整的 Spring Security 自动配置，避免为一个哈希函数引入整套过滤器链
- **数据源密码**：**AES/GCM/NoPadding**，每次生成随机 12 字节 IV，密文格式为 `{密钥版本}:` + Base64(IV ‖ 密文 + 认证标签)
  - 相较 ECB：GCM 为认证加密，自带完整性校验；随机 IV 保证**相同明文不会产生相同密文**
  - 保留只读的 ECB 解密分支，用于存量数据迁移
  - 密钥长度在启动阶段校验（16 / 24 / 32 字节），配置错误时立即失败，而非在运行期抛出难以定位的异常

#### 密钥版本化：让"换密钥"成为可能

密文前缀里的不再是固定的 `v1`，而是**密钥版本号**：

```
加密：永远用 aes.current-key-version 对应的密钥，并把版本号写进前缀
解密：按密文里带的版本号选密钥
```

一把"换不了的密钥"实际上等于"永远用同一把密钥"——密钥一旦泄露也换不了，
只能让用户把每个数据源密码重新填一遍。版本化之后轮换分三步，每步都可以停下来：

```yaml
# ① 加新密钥、切当前版本（老数据仍然解得开）
aes:
  current-key-version: v2
  key: <新密钥>
  keys:
    v1: <老密钥>

# ② 把存量数据重新加密到 v2：启动一次，幂等，跑完改回 false
aes:
  reencrypt-on-startup: true

# ③ 确认没有 v1 残留后，删掉 keys.v1
```

只配 `aes.key` 时行为与改造前完全一致（现有部署不需要改配置）。

> ⚠️ **残留边界**：密钥仍以明文形式存在于环境变量中，
> 没有解决"进程被攻破就能拿到密钥"。真正的密钥管理要把加解密变成一次远程调用
> （KMS / Vault 之类），密钥永远不落到业务进程。

### 6. 异步导出

导出任务通过 RabbitMQ 异步执行：接口仅写入一条 `PENDING` 记录即返回，消费者执行后推进状态机 `PENDING → RUNNING → SUCCESS / FAILED`，失败原因落库可查。CSV 输出对引号、逗号与换行做了转义处理。

三个容易被忽略、但缺了就会出事的点：

- **幂等**：MQ 只承诺"至少一次"，同一个 taskId 被消费两次是**常态**。
  用一条条件更新去"认领"（`UPDATE ... WHERE status='PENDING'`），影响行数为 0 就跳过。
  用 SQL 而不是"先查状态再判断"，是因为后者两个消费者可能同时读到 PENDING。
- **卡单补偿**：导出链路跨了"数据库 → MQ → 消费者"三段，每段失败都会留下一个**不会自己变**的状态。
  定时任务同时扫 `PENDING`（消息没投出去）与 `RUNNING`（结果没写回去），
  超时就标记为失败 —— 否则前端就是一个永远转圈的进度条。
- **可靠投递**：publisher-confirm + 死信队列 + 手动 ACK，三件缺一不可。
  只做 Broker 持久化时，处理不掉的消息会被**直接丢弃且没有任何痕迹**。

> 另有一层：导出文件有保留期，过期由定时任务删除并把数据库里的路径置空，
> 接口只下发"能不能下载"而不下发服务器路径。

**导出链路和查询链路一样有两个执行保护**（这两样是后来补的，见下）：

| | 查询链路 | 导出链路 | 超限行为 |
|---|---|---|---|
| 查询超时 | 30 秒 | 300 秒 | 中断并置 FAILED |
| 行数上限 | 1000 | 100000 | 查询**截断 + 标记**；导出**整个任务失败** |

> ⚠️ 两者超限行为**刻意不同**：查询结果就在屏幕上，用户看得见少不少，所以截断加标记就够了；
> 而**截断的 CSV 看起来是"完整的"** —— 用户会以为数据齐了拿去用。
> **静默的假数据比一句报错危险得多。**

### 7. 多方言支持（MySQL / PostgreSQL）

方言相关的知识全部收在一个枚举 `SqlDialect` 里，每个方言必须补齐六件事：
**连接串前缀、驱动类名、默认端口、危险函数名单、系统库名单、专有语法开关。**
少任何一个都是一处静默错误 —— 所以"加一个新数据库"现在是一件可以照着做、不容易漏的事。

三个真正体现"方言差异"的点：

| 差异 | 说明 |
|---|---|
| **危险函数与系统库完全是两套名字** | MySQL 是 `sleep` / `load_file`；PostgreSQL 是 `pg_sleep` / `pg_read_file`。拿一份名单去检查另一种数据库的 SQL，表现是"检查通过了但什么都没检查" |
| **`connectTimeout` 参数名相同、单位不同** | MySQL 是**毫秒**，PostgreSQL 是**秒**。把 5000 毫秒直接塞给 PG，等于设了一个 5000 秒的超时 —— 也就是没设 |
| **PG 的 `pg_catalog` 默认在 `search_path` 里** | `select * from pg_shadow` **不带库名前缀也能访问**。只检查"库名前缀"的实现在 PG 上会整个漏掉这一类，所以方言里额外有一个"裸表名"名单 |

`SqlValidateUtil.validate` **强制要求传方言，不提供省略的重载** ——
多一个"忘了传"的口子，就等于多一条"看起来在检查、其实没检查"的路径。

前端的数据库类型下拉框读 `GET /api/datasource/dialects` 生成，不维护第二份类型清单；
切换类型时自动带出默认端口（3306 / 5432）。

### 8. 审核工单与自然语言生成 SQL

写语句不再立即执行，而是先落一张工单，由**另一个管理员**看过影响面之后再决定执不执行。

**为什么需要这一层**：`SqlPermissionService` 回答的是"这个角色有没有资格执行写语句"，
工单回答的是"**这一条具体的 SQL 该不该放行**"。票务、文物这类数据，
一条 `UPDATE` 改错就是钱和档案的问题 —— 光有角色权限不够，还需要另一个人的判断。

三个必须分清的概念：

| 问题 | 由谁回答 |
|---|---|
| 能不能**直接执行**写语句 | 角色白名单 `role-whitelist`（走 `QueryServiceImpl`） |
| 能不能**申请**执行写语句 | `reviewable-types`（默认 INSERT / UPDATE / DELETE，**不看角色**） |
| 这一条**该不该放行** | 审批人 |

> ⚠️ 第二条最容易搞错，也最致命。如果提交工单也套用角色白名单，USER 连一条 `UPDATE` 的
> 工单都提交不了 —— 而"让没有写权限的人能够申请写操作"正是工单系统存在的理由。
> 但**放宽的只是语句类型**：解析、AST 危险函数、系统库、字符串兜底这四道防线，
> 在**提交和执行两处**各跑一遍，一道都没少。可申请的是"写语句"，不是"危险语句"。

状态机 `PENDING → APPROVED → EXECUTING → EXECUTED / FAILED`，外加 `PENDING → REJECTED`。

#### 执行留痕：前镜像 + 反向 SQL（闭环「批错了怎么办」）

审批类系统真正难回答的不是「该不该执行」，而是「**执行错了怎么办**」。
所以工单执行时会顺手把改动**前**那几行留一份：

```text
① 解析 → 只接受单表 UPDATE / DELETE
② 查主键 → 没有主键就没法定位行（记 SKIPPED）
③ SELECT * FROM t WHERE <原样的 where> LIMIT n+1 FOR UPDATE   ← 前镜像（顺带锁住这几行）
④ 执行原语句
⑤ 按主键重查                                          ← 后镜像
⑥ 由前后镜像的差异生成反向 SQL，落库                    ← 给人核对用
⑦ 提交（③~⑦ 在同一个事务里）
```

⚠️ **平台没有任何接口会执行反向 SQL。** 要回滚，就把它复制出来
**作为一条新工单提交**，走完全相同的审批路径 —— 因为回滚本身也是一条写语句，
而「刚改错了数据、人最急」正是最不该开直通口子的时刻。
这和项目里另外几处是同一个形状：`EXECUTING` 卡死标失败而不自动重跑、
写语句绝不自动重试、死信队列只可见不自动重放。

边界（都会记成 `SKIPPED`，即「这次没有回滚依据」，**而不是**拒绝执行）：
多表更新 / DDL / INSERT、目标表没有主键、超过 `review.undo.max-rows`（默认 200）、含二进制列。
取像与执行在同一个事务里，所以「改了但没留痕」和「留了痕但没改」都不会发生。
`REJECTED` 是独立于 `FAILED` 的终态 —— 混在一起会让"驳回了多少"永远统计不出来。

四个刻意的决定：

- **执行的是工单里存的 SQL**，审批接口的 DTO 里**根本没有** `sql` 字段。
  否则就是"审批人看到 A、实际执行 B"，而这个约束被固定在**数据结构**上，
  而不是靠"开发者记得别用前端的 SQL"。
- **不能审批自己提交的工单**（`review.allow-self-approve` 默认 false）。
  提交侧刻意不看角色，于是审批这一步就是整个流程唯一的兜底。
- **批准之后异步执行**：审批是一次状态变更（毫秒级），执行是另一件事。
  同步执行的话，一条慢 UPDATE 会卡住审批人的请求，网关一超时他看到"失败"，
  **而数据库里那条 SQL 其实还在跑、而且会跑完**。
- **执行失败绝不自动重试**：导出失败重跑一次没有副作用；
  `UPDATE t SET n = n + 1` 跑两次就是加了两次。所以执行中断时标 FAILED 并写明
  "是否已生效**无法确定**，请先核对数据" ——
  **把不确定性交给人，而不是用一个"重试"把不确定性变成实际的错误数据。**

**自然语言生成 SQL**（默认关闭）：业务同学用一句中文描述想改什么 → 模型生成 SQL →
过**完全相同的四道防线** → 落成待审工单。工单里同时躺着
**用户的原话**、**模型生成的 SQL**、**影响面预估** ——
审批人审核的对象从"一段代码"变成了"一个意图"，**审核在这里才真正成立**。

> **AI 没有任何特权**：同一条路径、同一套四道防线、同一个状态机、同一个执行消费者，
> 区别只是 `generated_by` 记成 `AI`、多存一句原话。
> 刻意没有做"AI 生成的所以检查松一点"—— 那样的路径会立刻成为整个系统里最薄弱的一环。
> 提示词里写的约束是**效率优化**，**不是安全边界**：模型完全可以无视它，
> 而我们必须假设它一定会无视。

接口按 OpenAI 兼容协议调用，换模型只改 `base-url` 和 `model`；
文旅 / 文物客户要求私有化部署时，要改的就是这一个配置。
⚠️ 打开之后**表结构会被发给模型服务**，这是一次真实的数据出境，所以默认关闭、由部署方显式签字。

> `SQL查询平台-审核工单与NL2SQL落地方案.md`。

## 请求链路

### 查询请求

```text
POST /api/query/execute
  │
  ├─ JwtInterceptor     校验 Bearer Token → 查 Redis 黑名单 → 写入 UserContext(ThreadLocal)
  │
  ├─ QueryController    滑动窗口限流（Redis + Lua，可配，默认 60 次 / 60 秒）
  │
  ├─ QueryServiceImpl   ├─ 校验数据源归属与启用状态
  │                     ├─ 按角色取语句类型白名单（SqlPermissionService）
  │                     ├─ SqlValidateUtil 解析 + 类型白名单 + AST 危险检查（按数据源方言）+ 字符串兜底
  │                     ├─ ConnectionManager 按方言取该数据源的 HikariCP 连接
  │                     ├─ setMaxRows(1001) / setQueryTimeout(30)
  │                     └─ statement.execute() → 有结果集则截断到 1000 行并置 truncated，
  │                        没有结果集则返回 affectedRows（写语句走这条分支）
  │
  ├─ QueryHistoryService 记录历史（成功 / 失败、耗时、错误信息）
  │
  └─ AuditLogAspect     AOP 记录写操作审计日志
```

### 导出任务

```text
POST /api/export  →  校验数据源归属 + SQL 审核（同一入口，但固定只允许 SELECT）
                  →  落库 ExportTask(PENDING)
                  →  RabbitMQ 投递 taskId
                  →  ExportConsumer 消费 → RUNNING → 执行 SQL → 写 CSV
                  →  SUCCESS / FAILED（错误信息落库）

GET /api/export/{id}/download  →  校验归属 + 任务状态 → 流式写回 CSV
```

## 测试与 CI

测试分为两层，其中单元测试不依赖任何外部中间件：

| 层 | 命令 | 依赖 |
|---|---|---|
| 单元测试 | `mvn test` | 无（AES、JDBC URL、SQL 校验、方言、分页、密码链路等纯逻辑） |
| 集成测试 | `mvn test "-Dsurefire.excludedGroups="` | MySQL / Redis / RabbitMQ；PostgreSQL 用例另需 `docker compose up -d postgres` |

需要中间件的用例标注了 `@Tag("integration")`，由 surefire 默认排除。

> ⚠️ **必须带上 `-Dsurefire.excludedGroups=`**。
> 排除项原本是硬编码在插件配置里的，而 POM 里显式配置的插件参数优先级高于命令行 `-D` 属性 ——
> 只写 `-Dgroups=integration` 的话，一条集成用例都不会跑，却会显示 BUILD SUCCESS。
> 现在排除项已改成属性（`surefire.excludedGroups`），所以清空它就能放行。

当前共 **342 个用例**：纯单元层 **306 个**（`mvn test`，不依赖任何中间件），
另外 **36 个**打了 `integration` 标签、默认不跑。集成用例覆盖：
MyBatis-Plus 装配与分页、导出的幂等与卡单补偿、**真实 PostgreSQL 下的双方言行为**、
写语句执行与角色权限、**审核工单的端到端链路**（提交 → 审批 → MQ → 执行 → 留痕）。

> 那条端到端用例里最关键的设计：探针表用的不是 `SET v = 42`（跑两次也是 42，看不出来），
> 而是 **`SET v = v + 1`** —— 它**不幂等**，一旦被执行两次，值就会变成 2。
> 然后测试**手工再投一次同样的消息**，断言值仍然是 1。
> 挡住重复执行的是消费者那个"只有当前状态是 APPROVED 才能认领"的条件更新。

> ⚠️ 集成用例需要 `DB_USERNAME` / `DB_PASSWORD` / `JWT_SECRET` / `AES_KEY` 四个环境变量。
> 不设的话第一个 Spring 上下文加载就会失败（`aesUtil` 初始化），
> 后续所有集成用例统一报 "ApplicationContext failure threshold exceeded" ——
> 看起来像"十几个用例坏了"，实际只是没设环境变量。

单元测试覆盖的失败模式：AES 加解密与**密钥轮换**、JDBC URL 的方言差异与超时参数、
SQL 校验（多语句 / 危险函数 / 系统库 / 可执行注释 / 空名单 / 按方言取名单）、
缓存击穿（32 线程并发只回源 1 次）、JWT 单次请求验签次数与剩余有效期换算、
CSV 导出编码、导出文件清理、数据源入口与状态校验、并发重名、缓存序列化、
全局异常语义、指标定义、角色权限矩阵、注册 / 登录 / 改密码链路、
审核工单（状态机 / 越权 / 并发审批 / 幂等键载荷比对 / 四眼原则）、
工单执行消费者（幂等认领 / 执行前重校验 / 回写令牌 / 时间戳时钟）、
工单补偿任务（重投 vs 判失败、绝不自动重试）、影响面预估的**文案**（扫描行数 ≠ 影响行数）、
表结构读取的三个上限与截断说明、自然语言生成（AI 无特权 / 哨兵 / 提示词 / 代码围栏剥离）、
以及一条**全项目级**的结构性守卫：任何 `@RequestBody` 参数少了 `@Valid` 都直接变红。
以及投递失败计数器 `mq_publish_failed{link=export|review}` —— 两条链路对"投递失败"的处置相反
（工单吞掉等补偿重投 / 导出立刻标失败），但**共同点是失败之后系统仍然看起来正常**，
所以这个计数器就是那句告警规则本身：**持续大于 0 就是 Broker 出问题了**。

还有一条跑在**真实 RabbitMQ** 上的死信链路用例：自己 `basicGet` 再 `basicNack(false,false)`，
断言消息**真的出现在自己的 `export.dlq` / `review.dlq` 里、且没有串到另一条链路**，
并验证 `mq_queue_depth` 指标确实指向对的队列。

这一轮补上的：队列容量参数与**双死信链路隔离**、**消息体是 JSON 而不是 JDK 序列化**
（含「默认转换器的产物确实以 Java 序列化魔数 `0xAC` 开头」这条对照断言）、
导出链路的**退避重试**（瞬时故障恢复 / 重试用尽进死信 / 次数可配 / 等待被中断），
以及一条**反方向的守卫**：工单链路落库失败进死信时，`UPDATE` **只允许执行过一次** ——
谁要是给它也加一个重试循环，这条用例会立刻变红。

> 最后那条是补出来的：给审批接口传 600 字意见，拿到的不是"意见过长"，
> 而是服务层那句"工单已被处理过" —— `@Size(max = 500)` 从头到尾没被执行过，
> 因为 `@RequestBody` 上少了 `@Valid`，约束注解退化成了注释。
> **单元测试全都通过也发现不了它**（被测的是服务层，校验发生在 Spring MVC 的参数解析层），
> 是靠一次真实 HTTP 调用才暴露的。

## 已知限制

> 这一节曾经列着 5 条限制。其中 4 条已经修掉，保留在这里是为了说明**每条当时是怎么想的、现在做到了什么程度** ——
> 一条限制被划掉的方式，比它存在与否更能说明问题。

| # | 曾经的问题 | 现状 |
|---|---|---|
| 1 | SQL 审核的关键字层基于字符串匹配，可被注释拆分绕过 | ✅ **已改为 AST**（+ 两个精确的字符串兜底）。见「核心设计 §1」 |
| 2 | 多实例部署时缓存失效不彻底 | ✅ **已加 Redis 发布订阅广播**。并更正了原表述：真正需要同步的是**连接池**，缓存本来就在 Redis 里 |
| 3 | 缺少监控与指标 | ✅ **已接入 Actuator + Micrometer**，四项均可查 |
| 4 | AES 密钥仅环境变量注入，无轮换 | ⚠️ **部分解决**：已支持密钥版本化与轮换迁移；但密钥仍以明文存在于环境变量中 |
| 5 | 权限模型未按角色区分 | ✅ **已落地**：角色 → 语句类型矩阵可配，管理员通过邀请码注册 |

**当前仍然存在的边界**（都是有意保留、且写明了理由的）：

1. **密钥的保管方式**：版本化解决了"换不了"，但没解决"进程被攻破就能拿到密钥"。
   真正的密钥管理要把加解密变成一次远程调用（KMS / Vault 之类），密钥永不落到业务进程。
2. **应用层校验挡的是"手滑和顺手"，不是"铁了心的攻击者"**。
   真正的兜底是数据库侧的只读账号 —— 应用层无论被怎么绕过，最终能在数据库上做的事情仍被账号权限限制着。
3. **CI 不验证"应用能不能启动"**：唯一加载 Spring 上下文的用例打了 `integration` 标签，
   而 CI 跑的是默认的单元测试层。所以任何**只在启动时才会暴露**的配置错误
   （占位符解析不了、配置绑定失败）CI 拦不住，只能在人肉启动时发现。
   补法有三个方向：CI 里用 Testcontainers 起中间件、用内存替身跑一个冒烟测试、
   或者加一个"只验配置绑定与上下文刷新"的轻量检查。
4. **限流是进程内实现**：它负责"拦住失控的脚本"，不是"扛住大流量"。
   真要在大流量下守住，靠的是网关层限流。
5. **RabbitMQ 的队列参数（或消息格式）变更需要人工升级**：队列参数是**队列本身的属性**，
   给一个已存在的同名队列改参数，Broker 会用 `PRECONDITION_FAILED (406)` **拒绝声明**，应用会因此起不来。
   升级到当前版本需要做两件事：

   ```bash
   # ① 删除旧队列（应用启动时会按新参数重新声明）
   docker exec sql-query-rabbitmq rabbitmqctl delete_queue export.queue
   docker exec sql-query-rabbitmq rabbitmqctl delete_queue review.queue
   # ② 两个队列现在都带 x-max-length=10000 + x-overflow=reject-publish-dlx
   #    确认方式：
   docker exec sql-query-rabbitmq rabbitmqctl list_queues name arguments
   ```

   ⚠️ **死信链路的最后一跳是整条可靠性链条上唯一没有兜底的地方**：被 `nack` 的消息由 **Broker**
   送去死信交换机，所以 `mandatory` + returns 回调那一套**在这里不生效** ——
   路由键写错时消息既不报错也不退回，**直接静默丢弃**。（这是做反向验证时确认的，见档案 G-02。）

   ⚠️ 第二步同时也是**消息格式的切换点**：消息体现在是 JSON（`Jackson2JsonMessageConverter`）而不是 JDK 序列化。
   删队列之前**请先确认队列是空的**，否则里面那些 JDK 序列化的旧消息会被新消费者反序列化失败 → nack → 进死信。
   （本次升级时两个队列都是 0 条消息。）
6. **自然语言生成 SQL 默认关闭**：它要读表结构并**发往外部模型服务**，这是一次真实的数据出境，
   打开前需要有人为此签字。**前端页面尚未实现**，只验证了后端接口与契约。
7. **工单链路自身新增的边界**：工单表没有保留 / 归档策略、无法撤回已批准工单、
   补偿任务是头部优先、`SchemaIntrospector` 的缓存是 JVM 内的。

   > ✅ 这一条里原来还列着「执行失败无法自动回滚」和「批准成功但投递失败只有日志没有指标」，
   > **两条都已经闭环**：前者见上面第 8 条（前镜像 + 反向 SQL，档案第十三章），
   > 后者见 `mq_publish_failed{link=export|review}` 计数器（档案 G10）。
   完整清单与逐条理由见 `SQL查询平台-审核工单与NL2SQL落地方案.md` 第 7 节。

   > ✅ 这一条里原来还有一句「`ExportConsumer` 的回写有同款潜伏缺陷（本轮未改）」——
   > **已经修了**：导出链路的回写改成了带认领令牌的条件更新（`WHERE status = 'RUNNING'`），
   > 并把卡死判定从 `created_at` 换成了 `started_at`（见档案 G-01）。

8. **工单执行的前镜像留存有明确的覆盖边界**（见档案第十三章）：只覆盖**单表 UPDATE / DELETE**、
   要求目标表**有主键**、默认最多留存 **200 行**，且不含二进制列；其余情况会记一条 `SKIPPED`
   ——也就是「**这次没有回滚依据**」，而不是「不会出事」。取像用 `FOR UPDATE` 锁住被改的行。
   ⚠️ 反向 SQL 的正确性依赖前镜像：**前镜像若取错，回滚就是第二次破坏**，所以回滚必须由人核对后提交。

9. **⭐ 压测量出来的两个真实瓶颈，以及一个「量出来但没修」的缺陷**（完整数据见 `高并发压测报告.md`）：

   - **业务数据源连接池的 5 条连接是第一个瓶颈**。它表现为「并发越高成功吞吐越低」
     （并发 8 → 64 时，296.5 → 87.5 QPS，错误率 14% → 92%）；
     把并发闸门放大到 1000 之后，同样负载是 **570.8 QPS / 0% 错误**。
     测出来的是「5 是瓶颈」，**没有**验证「调大就能解决」—— 那是容量规划，不是改一个常量。
   - **第二个瓶颈是应用主库的 Hikari 池（max=10）**，它是 ~570 QPS 那个平台值的真因
     （每个查询请求要写 2 次主库）。
   - ⚠️ **未修**：被并发闸门拒绝的请求**仍然会往主库写一条审计日志**
     （`AuditLogAspect` 是 `@Before`，跑在 Service 层的闸门之前）——
     **闸门保护了业务库，代价却记在主库上**，这正是上面那个负向扩展的根因。
     三条候选修法各有代价，本轮没有在没想清楚的情况下动请求生命周期，详见档案 G-07。

10. **压测是在一台开发机上做的，数字只能横向对比**：压测客户端、应用、MySQL、Redis、RabbitMQ、
   PostgreSQL 全在同一台 16 核机器上，且压测期间机器上还有其它进程在工作，
   **不能用作容量规划**。报告里单独用两节逐条列了「没测到的」和「不可靠的」。

11. **⭐ 数据库跑的是「双1」，而它的成本以前从没被算过**（详见档案 G-08）：

    - 服务器实际配置：`log_bin=ON` / `binlog_format=ROW` / **`sync_binlog=1` +
      `innodb_flush_log_at_trx_commit=1`（双1）** / 全部 8 张表 InnoDB。
      这是 MySQL 8 的**默认值**，所以从来没人看过它 —— 但它一直在收钱。
    - 而全项目 **`@Transactional` 只有 1 处、且写在注释里**，所以**每一次写都是独立的
      autocommit 事务**：一次查询请求写 2 张表（`audit_log` + `query_history`）= **2 次提交**
      = 4 次 fsync（redo + binlog，两阶段提交）。
    - 实测（2000 行，同一台机器）：双1 + 逐行提交 **175 行/秒**；非双1 + 逐行提交 4,649 行/秒；
      **双1 + 单事务 7,053 行/秒**。⭐ **批量提交比关掉持久性还快** ——
      **想快，正解是减少提交次数，而不是牺牲耐久性。**
    - 这解释了上面那个 570 QPS 天花板的**底下那一层**：570 × 2 = **1,140 次提交/秒**，
      而这台机器 10 连接下的提交速率实测约 **1,054 次/秒**。两者几乎相等 ——
      **所以「把连接池调大」大概率提高不了这个数**（连接数只是通向 fsync 的管道）。
      ⚠️ 这一条是**两个实测数字相比得出的推断**，不是直接测出来的。
    - **有意不改**：这是审计类平台，为了性能把「掉电不丢已提交事务」换掉，等于把地基换掉。
      **该做但没做的是合并写**（把每请求 2 次提交变 1 次）—— 那能砍掉一半提交且不动耐久性。
    - ⚠️ **`binlog` 目前是纯成本、零收益**：开着、`ROW` 格式，但没做复制、没做过恢复演练、
      也没利用它里面的前后镜像 —— 而工单「写语句无法回滚」（L6）的解法正好在那儿。

## 安全说明

- 数据库密码、JWT 密钥与 AES 密钥均通过环境变量注入，不写入配置文件
- **管理员邀请码同样只从环境变量注入**，且默认关闭 —— 它是一个凭据，不要写进配置文件或提交进仓库
- 登出黑名单**存 token 的 SHA-256 哈希**而不是原文：原文入库等于把一把还能用的钥匙抄一份放缓存里，
  Redis 一旦被读就能直接重放登录态，且不需要 JWT 密钥
- 监控端点走**独立端口 8081 且只监听 127.0.0.1**，暴露白名单只开 `health,info,metrics,prometheus`；
  `/actuator/env`、`/beans`、`/heapdump` 之类默认就是关的
- 健康检查的开关也跟安全取向一致：`liveness` 只看进程本身，`readiness` 只看平台自己的数据库，
  **刻意不含 Redis** —— 否则负载均衡会因为一个"可以降级"的依赖把实例摘掉，等于把"降级可用"又变回"不可用"
- `sql/schema.sql` 中创建的 `query_user` 仅授予 `SELECT` 权限，建议使用该账号连接业务库，与应用层 SQL 白名单形成多层防御
- `docker-compose.yml` 中的凭据仅用于本地演示，部署前必须替换
